Look at Ultimate's UI and drive fresh headless Chromium pages with `screenshot` and `browser`. After UI changes, inspect the returned image rather than assuming the page renders.

Install Chromium separately; playwright-core does not download browsers. Resolution checks `ULTIMATE_CHROMIUM`, `/usr/bin/chromium`, `/usr/bin/google-chrome-stable`, the newest Playwright Chromium (`~/.cache/ms-playwright/chromium-*/chrome-linux64/chrome` on Linux, `~/Library/Caches/ms-playwright/chromium-*/chrome-mac-<arch>/Google Chrome for Testing.app` or `chrome-mac/Chromium.app` from older Playwright releases on macOS), then `/Applications/Google Chrome.app`. Google Chrome comes last because a managed Mac's Chrome policy can disallow remote debugging: Chrome then closes its connection a few seconds after its first page (its log says "DevTools remote debugging is disallowed by the system admin") and every call fails with "Target page, context or browser has been closed". On such a machine run `npx playwright install chromium`. Chromium's sandbox is enabled by default; Linux requires unprivileged user namespaces or a working setuid `chrome-sandbox` helper. Set `ULTIMATE_CHROMIUM_SANDBOX=0` before starting Ultimate to disable it only if your environment cannot support sandboxing. A browser is launched lazily and closed when the host shuts down; one that disconnects (crashed, or dropped its connection and kept running) has its process group killed, and the next call launches a fresh one. Each call has its own isolated context, closed on completion or cancellation.

No call can hang: loading, each step (including `eval`, which Playwright never times out) and the capture each time out after 30 s (`timeoutMs` overrides it), and a whole call after four such limits plus its explicit waits. Launching the shared browser and opening the call's page come before that budget and get at least 30 s, so a short `timeoutMs` limits the steps, not a cold launch on a loaded machine. A timed-out step fails the call with a `TimeoutError` on its `Step n:` line. Closing a context is bounded too; a context that will not close (a wedged renderer) closes the shared browser, so the next call launches a fresh one.

`screenshot` accepts url, path, viewport dimensions (1440 × 900 by default), selector, fullPage, waitMs (1500 by default) and light/dark theme. A page of this host's own UI is detached from the shared durable UI state: it reads it once at load, then its `?conversation=`, panels and clicks stay its own, so a driven page never moves the user's tabs. For own-UI screenshots, theme initializes this isolated browser's `ultimate.theme` localStorage preference before navigation. Other URLs receive only the browser color-scheme preference. `url` is the page to load; a relative one such as `/` (which opens @ultimate, as every page without `?conversation=` does) or `/?conversation=<id>` resolves against this UI. `path` is where the full-resolution PNG is saved: it must end in `.png`, resolves against the conversation's cwd (its worktree in an isolated workspace), and missing parent directories are created. Without it the PNG goes to `$ULTIMATE_HOME/screenshots`. Either way the result names the absolute file; Pi Durable's `fitImage`, on the host's shared Photon processor (`host.images`, also used by `read`), returns compact PNG or JPEG images capped at 1600 pixels on the longest side, within its default byte limit. Resized images include a note for mapping coordinates to the original. If an image cannot fit the limit, the tool returns the PNG path without an inline image. Loading console and page errors accompany the title and PNG path.

`browser` accepts the same url, path and viewport dimensions (`width: 375` for a phone check), click/fill/press/wait/eval/send/until/ui steps and an optional final screenshot (default true). `wait` takes a selector only; there is no fixed-time wait. On an Ultimate page, `click`, `fill` and `press` first wait for the same readiness as `ui` steps, so no step needs a sleep before it. Every page it drives is marked `ultimate.driven`, so an Ultimate UI, this one or a preview, installs `window.ultimate` (`web/src/sdk/test-hook.ts`) from its own stream: `send` submits a prompt to the shown conversation (or `conversation`), and `until` resolves on the store change that makes its condition hold: `'idle'` (that conversation's sent turn ran and is no longer busy; a turn too short to show busy counts by its answer time), `'quiet'` (no conversation busy), `{entry: kind}` (a new entry of that kind), `{event: name, where}` (a durable event from the root's feed whose data matches `where`) or `{ui: label, is}` (the control with that exact label or ref has every state in `is`, like `{checked: false}`; without `is`, it is on the page). A `ui` wait rechecks on each component change the bridge reports and each DOM change, and resolves with the component. After a `send`, entries and events count only from it. `until` gets its own budget, 10 s unless `timeoutMs` (at most 120 s, for waits on a model turn), and on timeout names what was still busy or what arrived instead. An `{event}` wait fails at once on a name the page's server does not define (naming the close ones), and when an event that `fails` the awaited one arrives (`workspaces.landing-failed` for `workspaces.landed`). A steer queued during an `until` ends the call with the steps so far, as it ends an interruptible bash call; later steps do not run. A page without the hook fails the step with that reason.

Drive ui-sdk controls (switches, selects, dialogs, anything `@/components/ui` builds on ui-sdk) with `ui` steps, through the page's agent bridge (`web/src/sdk/agent.ts`, exposed as `window.ultimate.ui`), not with selectors. Each `ui` step waits until the page has rendered its surface with every facet loaded and every mounted read has its first answer (or failed to reach the server), so the first step needs no wait for a selector: `{ui: 'snapshot'}` returns the controls on the page, each `{ ref, component, label, state…, actions }` (ones that left the page are dropped); `{ui: 'query', text?, within?, kind?}` finds controls by label or row text, or a list's items `within` one; `{ui: 'act', steps: [{ref, action, args?}]}` runs actions in order, `ref` a snapshot ref or the label (`[{ref: 'Keep warm', action: 'setChecked', args: [false]}]`); a label that exactly names one control on the page acts on it, even when other labels contain it as a word (ui-sdk alone ranks those together and can press a transcript row named "read live-system.png" for `System`), and returns what changed; a failed action fails the step with its error, naming the action, and later steps do not run. Each change reports `source: 'agent'` to the component; a kit control's write to stored state (UI state or an action) then carries `x-ultimate-source: agent`, and the server records it as a `ui.changed` event in the same commit (`extensions/ui/README.md`). Every other write from a driven page (a scripted click or keypress) is the agent's too. Before it closes the page, after any last step, the tool waits (within the call's deadline) for the page to send its pending UI-state writes, so a final click still leaves them with their event; a call cancelled by its caller closes at once. Values inside `data-agent-secret` read `"[redacted]"`; controls inside `data-agent-hidden` do not appear; a step on a `data-agent-confirm` control fails with "Needs a person".

A driven page on a preview saves its own UI state (`ext.*` keys, such as a switch an agent turned) like any tab, so it shows up for the user, marked as the agent's; `shell.*` keys (conversation, surface, panels, sidebar, dock), which move the view, stay in that page. A page on this host's own origin (detached) saves nothing.

Click only what you are testing. Set up everything else (model, thinking, Play/Pause, abort, compact) through `window.ultimate.api`, the page's own SDK client (`web/src/sdk/api.ts`), in one `eval` step, or curl the preview's HTTP API; then wait with `until`, never a fixed `wait <ms>`. Switching conversation 2 to another model: `{eval: "window.ultimate.api.configure({model: {provider: 'openai-codex', modelId: 'gpt-6.1-sol'}}, 2)"}`. Likewise `api.configure({thinkingLevel: 'high'}, id)`, `api.abort(id)`, `api.compact(undefined, id)` and `api.action({extension: 'pause', name: 'play'}, null)` for any extension action. In a preview, standing agents (@ultimate, @lander) stay on `instance.model`; a model switch sticks on a conversation you create (`api.createConversation()`).

`where` compares fields of the event's data, so a key the event does not carry never matches and the step waits out its budget. Events carry ids and counts, never text: `user.input` is `{conversation, kind: 'prompt'|'steer'|'follow-up'|'answer'|'dismiss'|'review', entry?, submission?, message?, length}`, `board.sent` `{message, from, to, reply, steer}`, `subagents.started` `{id, agent, model?, thinking?, parent?, kind: 'child'|'standing'|'branch'}`, `coding-tools.committed` `{conversation, sha, parents, repo, worktree?, branch?, subject, rewrittenFrom?}`, `workspaces.check` `{submission, command, result, ms}` and `workspaces.landed` `{conversationId, sha, base, target, lander, title, commits, paths, …}`; every other event's fields are in the `defineEvent` of its extension's `refs.ts` (or `shared/events.ts`). Entry kinds are what `window.ultimate.state()` lists (`pi.user`, `pi.assistant`, `pi.tool-result`, …); tool calls live inside `pi.assistant`, there is no `pi.toolCall` entry. JavaScript eval runs inside the page. Calls stream progress; screenshot is replay-safe, browser is not because interactions may submit prompts. Both are automatically available in codemode's `tools`; use `const shot = await tools.screenshot({}); if (shot.image) image(shot.image)` to display its image. Structured nested results include title, PNG file path, outcomes, and an image data URI.

`web.solid.tsx` renders `screenshot` as a thumbnail that opens full size, with the page title, PNG path, and loading errors, and `browser` as its steps with an outcome each (✓, ✗ with the error, the value an `eval` returned) and the final screenshot.
