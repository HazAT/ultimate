Model, thinking, and login, as Pi does them: a model button and a thinking-level button in the composer toolbar, a searchable model picker grouped by provider (availability, login status, context window, thinking, price per million tokens), and a login dialog that drives any pi-ai provider's flow, subscription or API key, with credentials shared with pi in `~/.pi/agent/auth.json`.

Picking a model calls `api.configure({ model })`; the server keeps the thinking level when the model supports it and otherwise clamps it with Pi's `clampThinkingLevel`, and the toolbar shows what it configured. A model whose provider is not logged in opens the login for that provider. The thinking menu offers the model's supported levels (Pi's `getSupportedThinkingLevels`), and Shift+Tab cycles them in Pi's order, like Pi. Commands: `model.pick`, `model.thinking`, `model.thinking.cycle` (Shift+Tab), `auth.login`; the status line's model opens the picker through `model.pick`.

A response that ran on another model or thinking level than the response before it gets a quiet divider above it (`model a → b · thinking high → max`), derived from what each stored response records, so it needs no writes, covers branches and older history, and shows where a change took effect rather than when it was picked. Each response records the thinking level its request asked for (`thinkingLevel`, through this repository's Pi Durable patch); responses from before that compare the level the provider reports (`providerThinkingLevel`), which only some providers do. `switches.ts` derives them.

A conversation whose model's provider has no login here (a removed credential, a moved default) switches when its next run's first input is placed (`fallback.ts`, the patched `beforeInput` hook, so typed inputs, deliveries and queued follow-ups alike). Only certain evidence switches: the model's provider is registered, the availability snapshot lacks the login and a fresh `checkAuth` agrees; a provider that is not registered (its extension did not load), or a pending, failed or timed-out check, keeps the model, and its run fails with "Model … is not available". It switches to the same model id on another provider with a login, else the model its definition pins (`Profile`, or the label of a branch or lander), else the configured default (`configuredModel` in `lib/agents.ts`), never to whatever model is first. A subscription login (Pi's `isUsingSubscription`; `anthropic` counts as pay-per-token here, since Claude runs on its subscription only through Claude Code) only switches to another subscription: without one it keeps its model and writes a "needs you" entry once. It writes one `models.fallback` entry, `{ from, to?, reason: 'same' | 'pin' | 'default' | 'none' }`, rendered as a card with Pick another and log in; the model reads one line. A run already under way fails once; the watchdog's card then says the provider has no login. New conversations never inherit a model without a login either: branches, standing agents, automation runs and the lander resolve explicit model → usable pin → default, and the root follows the default each time the home opens. The default is one answer for model and thinking level (`hostDefault` in `lib/agents.ts`).

Login is this extension's own: `server.ts` runs Pi's `modelRuntime.login` behind four actions, `login { provider, type }` → `{ flowId }`, `answer { flowId, value }` (an empty answer is an answer), `cancel { flowId }`, and `logout { provider }`. Each flow is shown in `models.login`, a document on the conversation that started it: status, the pending prompt, and the provider's events, never answers, credentials, or provider error details (a failed flow reads `Login failed`). Flows are process-local; one that dies with its process reads cancelled from the next start on. The dialog streams the document with `useDoc` and renders the events (`auth_url` with open and copy, `device_code` with a countdown, `info`, `progress`) and the `text`, `secret`, `select`, and `manual_code` prompts; closing it or the tab cancels a running flow, as does showing another conversation (the document stays with the one that started the flow), configured providers can log out, and a finished login or logout resets that provider's health to unknown (`extensions/health`) and refreshes the model list with `refreshModels()`, which every tab also calls when its window gains focus, for logins in another tab or in pi.

`picker.tsx` is the model picker (its `ModelRow` also lists models in the conversations extension's Summary model picker), `login.tsx` the login dialog, `state.tsx` the shared helpers (the current model, cycling, dialog ids, which provider the login opens on), `server.ts` the login actions and document.

## Model families

A family is a named role with one model, thinking level and color: `default` (shown as "Ultimate"), `review`, `fast`, `tiny` and `design` are built in (`lib/families.ts`) and the user can add more. Everything that calls a model runs on a family rather than a model: agent definitions name one (`family: fast`), summaries run on `tiny` and previews on `fast` unless the families' settings assign them elsewhere. Precedence for a definition: a `model` pin in its file, then its `family`, then `default`; an agent's family lives only in its definition, and an overlay naming a family replaces an earlier file's pin. The default family runs new conversations, @ultimate and branches; without a model of its own it follows Pi's default model and thinking, and subagents of the default family inherit their parent's model. Get ready's Continue sets the default family's model and thinking (`setDefault`; see `extensions/onboarding/README.md`). A `summaryModel` or `instance.model` setting pins its feature to one model; moving the feature to a family removes that user-settings pin.

The subagents extension's **Agents** panel is the one place to configure them (⌘K **Model families…** and the picker's row open it). Each family heads a group, its model and thinking on one line; clicking it opens the family's popover (`family-editor.tsx`): model, thinking, color, and **Remove** for a family the user added. **+ Family** adds one. Under each family sit the agent definitions and features that run on it, and last those that pin a model of their own. An agent row opens its definition; its **move** menu runs it on another family by saving its definition, which for a built-in writes an overlay holding only `family`. A feature's menu saves its assignment with the families; one the project's settings decide is fixed. A family change applies to conversations started after it; open ones keep their model. The definition form shows the family it runs on and links to the panel, or pins a model of its own.

Families are kept per project in `~/.ultimate/model-families.json`, keyed like the project's trust decision (a linked worktree shares its main checkout's), and each save is also the `recent` entry that every project without its own starts from (`lib/families-settings.ts`). A project's `.ultimate/settings.json` `modelFamilies` (`{ families, assign }`) is the team's default: it applies over `recent`, and a person's own families for the project apply over it, so saving stores only what differs from it; the family's popover says when it changes a family, and a feature it assigns cannot be moved there. `assign` holds features only (`summaries`, `preview`).

Families show with their color only where they are configured: the Agents panel and the definition form (`families.tsx`: `useFamilies`, `FamilyDot`, `FamilyLabel`, exported through `ui.tsx`). Elsewhere a model shows by its id, except the composer's model button and the picker's check, which name the family the conversation runs as: `models.family`, a document on the conversation (`Family` in `api.ts`). Whoever configures a conversation from a definition records it in the same commit (`definitionFamily` in `lib/agents.ts`: branches, subagents, automation runs, standing agents), the picker when it picks a family (`setFamily`) or a model by id (none), and a login fallback clears it. It is never worked out from the model, since two families can share one; a conversation without a record (the root, the lander, one from before the record) shows the default family only while it runs that family's model and thinking. The browser fetches the families once, again on window focus and after a save.
