Reports failed runs to their subagent owner or @ultimate.

A run fails with a provider error (`model_error`, `no_model`), or when restarts cut it off: the host stopped while the model was answering and no retry was left (`interrupted`), or the run was cut off Pi Durable's `restartLimit` times in a row (`restart_limit`). A run cut off by restarts is reported at once and never retried, because its last tool call may have partly run.

Provider errors classified as temporary by Pi, Claude Code relay responses that ended incomplete with status 200 or unknown, and model streams that stalled (`Model stream stalled: …`, which Pi does not retry by itself) get up to four continuations, after 1, 5, 15 and 30 minutes (`RETRY_DELAYS_MS`): a provider outage gets about 50 minutes to pass. Each continuation's request ID names the generation it continues (`watchdog-retry:<task>`); when that continuation fails too, the new report counts one more than the watchdog task it came from. A broken login (“not logged in”, a failed OAuth refresh, `invalid_grant`) is reported at once with a hint to log in again that names the provider (`diagnose` in `server.ts`). If the conversation is busy at that deadline, or ran again after the failure (even if that run failed too), watchdog leaves it alone. `subagent stop` cancels that child's pending watchdog task and withdraws any queued retry input, using the stop handler's captured identities so replay leaves later work alone. After the fourth failed continuation it reports, counting them (`retries`). Persistent and non-temporary errors become a `watchdog.failure` card with the conversation, title, error, last tool step and any login hint; reporting a subagent's failure marks its parent's `failed` action for it `given-up`. @ultimate's own failure becomes a display-only `watchdog.standing-failure` card in its own transcript, which starts no turn and is never folded; other failure cards fold like any entry. User Stops are ignored; reply-expecting Messages inputs already have a failure reply and are excluded. A `board.delivery` task that faults (the failure reply itself could not be sent) becomes a `watchdog.failure` card for the message's sender, or @ultimate when the user sent it, with step `message delivery`.

A root receipt and background task are created atomically for each failed generation; retry/report submissions use stable request IDs. On open, missed failures are scanned above the stored high-water mark, never advancing past unfinished work. Fresh installation marks existing tasks as historical and reports none of them.

Older transcripts may hold `watchdog.idle` notes from a retired idle-branches reminder; they still render. What each branch waits on now shows in the sidebar (`lib/waits.web.ts`).

Watchdog keeps the last 20 reported failures (`watchdog.reported` on the root, written with each report, including @ultimate's own) and serves them through `WatchdogApi.failures(since)`, newest first; the `status` extension reports them.
